# DiyDvrExtension version history

## 0.3.0

- **Capture now survives a reconnect.** The app re-runs the extension's `initPanel` whenever the live connection's presence or context changes, which tears down the panel and terminates its Web Worker — so the entire in-memory buffer was lost at exactly the moment something interesting happened on the wire. The panel now caches **clips** (non-destructive MCAP snapshots of the buffer) in OPFS, the origin's private file system, which outlives any single worker. A freshly-started worker reads the cache back, so clips are still listed after a reconnect.
- **Clips are captured automatically** on five triggers: the connection going quiet for longer than a configurable threshold (`gap>10s`), the tab being hidden (`backgrounded`), the tab or app closing (`closing`), each completed auto-save window (`auto-save`), and recovery of an interrupted session (`recovered`). There is also a **Cache clip** button for snapshotting on demand. Snapshotting never disturbs the live buffer, which keeps rolling exactly as before.
- **Rolling backup of the live buffer.** Between clips the current window is mirrored to OPFS every few seconds, guarded so builds never overlap and skipped when no new message has arrived. Whatever a terminated worker left behind is promoted to a `recovered` clip on the next mount, so a hard stop costs at most one mirror interval instead of the whole buffer.
- **Auto-save no longer loses windows, and is now a per-session choice.** A rotation clears its window from the live buffer as it hands it over, so anything that stops the file being written loses that window outright — and a folder's write permission drops back to "prompt" on every page load, which a rotation cannot re-request because it has no user gesture to do it from. Auto-save therefore paused indefinitely and dropped every window. Rotations now write to the clip cache like any other trigger, so the data survives regardless, and the folder write is treated as a bonus on top. Auto-save also starts **off** after every load rather than being restored from the layout, because turning it on is a gesture and therefore the moment the folder can be granted for the session. For the same reason the **save destination starts at browser downloads** after every load rather than presenting the last-used folder: a restored folder would look like the active destination while the grant behind it was gone. Picking a folder — the gesture that grants access — makes it active for the session, and it survives the panel restarts the app performs on a reconnect. A save that pauses, is denied, or fails is now reported in a coloured banner pinned to the top of the panel instead of a muted stat row.
- **A looping or replayed source no longer grows the buffer without bound.** The lookback was measured on the timestamps the source reports. A server replaying a recording on repeat — or a bag replay, or a backlog delivered after a reconnect — reports the recording's own time, which cycles back to the start on every loop, so the measured window never grew past the limit and nothing was ever dropped. The buffer gained a whole loop's worth of messages every cycle, climbing into gigabytes, while the panel showed a reassuring "9s / 10s". Measured on a looped stream: the buffer climbed by 120 messages every four seconds indefinitely, and now settles at one window's worth and stays there. The window is now measured on when the panel itself received each message, which is the one clock that always moves forward; each message's own timestamps are still recorded in the file exactly as before. There is also a hard size ceiling behind it now, which says so rather than capping silently, so no timestamp behaviour can run memory away again.
- **The rolling window now follows message arrival, not the sender's clock.** The buffer was ordered, measured, and trimmed by each message's *publish* time. On a merged multi-sensor stream — several cameras plus telemetry, each with its own clock and its own latency — publish times arrive out of order, so the window's ends jumped about: the reported span oscillated and the lookback trimmed in fits instead of filling smoothly. A single sensor whose clock ran ahead could collapse the window to almost nothing. It now keys on arrival time, which is what MCAP calls log time and what Foxglove recommends ordering on, while each message's true publish time is still recorded alongside it. Saved files therefore carry a faithful log time *and* publish time, and play back in the right order on the default timeline.
- **A steadier status readout.** The buffered span is reported in whole seconds rather than tenths — rounded up and capped at the limit, so a window the ring keeps just under its budget reads as full instead of sitting at one second short forever — and the live figures update once a second instead of every couple of hundred messages — which on a fast stream meant several updates a second in uneven bursts. Measured on a busy synthetic stream: 20 updates in ten seconds at an even one-second cadence, down from 50 arriving in sub-second clumps.
- **Two panels no longer fight over the recovery backup.** Whether a rolling backup could be adopted was decided by trying to delete it, on the assumption that a running panel would be holding it open. It isn't: browser storage locks a file only for the instant of a write, so a *live* panel's backup was deletable almost all the time — and a second DIY DVR panel starting up would take it, then lose that panel's buffer if it were interrupted before writing again. The backup now carries a heartbeat and is only adopted once it has stopped being refreshed, so a running panel's is never touched. Recovery arrives a few seconds later than before as a result, and a backup abandoned mid-session is now picked up while the panel keeps running rather than waiting for the next reload.
- **Bounded clip cache.** A new **Cache limit (MB)** setting (default 2048) caps the total; whole oldest clips are dropped first, except that recovery clips go before anything else. Only the most recent recovery clip is kept, so reconnecting repeatedly can no longer push out the clips you asked for. The live buffer and the rolling backup are never evicted.
- **New panel body, built for a small panel.** The three buffer controls — **Save to disk** (the primary action), **Cache clip**, and **Reset buffer** — plus a one-line status such as `● Recording — 0.5s / 60s` are pinned to the top, so they stay reachable however far you scroll and however short the panel is. The detailed stat rows sit behind a disclosure and are collapsed by default. Below that, a **Cached clips** list, which says when it is still reading the cache rather than showing an empty list: each row shows its trigger as a chip plus capture time, duration, size, and message count, expands into a per-topic message-count table, and carries its own save and delete controls. **Save all** and **Clear all** live in the Cached-clips header, with the cache-fullness meter that turns amber and then red as the cap approaches — eviction drops the oldest clip silently, so it is worth seeing coming. Destructive actions all confirm inline, including **Reset buffer**.
- **The panel says when capture could not start.** A host that forbids the panel from creating its worker (a stricter Content Security Policy, for example) produced a panel stuck on "Starting…" with the reason only in the developer console; it now shows the failure. Readiness is also reported by the worker itself rather than assumed the moment it is created, so a worker that fails on startup can no longer leave the panel claiming to be ready.
- **Recordings are written to storage as they are framed.** Both the rolling backup and every cached clip used to build the whole MCAP in memory and then copy it once more before handing it over, so each write briefly held two extra full copies of the buffer on top of the buffer itself. On a multi-gigabyte capture that repeated churn is what drove the app's memory upwards over a long session and never gave it back. The MCAP now streams straight into the file, so a write holds one chunk — around a megabyte — regardless of how large the buffer is. Saving to disk still produces the file in memory, since that is what gets handed to the browser to write, and reading a clip back is unchanged.
- **The rolling backup costs less on a large buffer.** Backing up a multi-gigabyte buffer takes seconds, and on a fixed timer that work grew with the buffer. The interval now scales with how long the last backup actually took, keeping it to a small share of the time whatever the buffer's size.
- **Slow actions say so.** Framing and writing a large window takes seconds, all of it in the worker, so **Cache clip** used to sit there looking untouched and get clicked again. It now disables itself and reads "Caching…" the moment it is pressed — before the work is dispatched — and comes back when the clip is confirmed. Per-clip **Save to disk** and **Save all** do the same, since reading a gigabyte back out of browser storage is not instant either. A stalled write cannot leave a control disabled for good.
- **Topics are split into Source and Generated.** Topics produced by user scripts (the `/studio_script/` namespace) now sit in their own group and are **not captured by default**; source topics stay on as before. Each group has enable-all / disable-all in its overflow menu. This came out of a customer report where a cached clip grew from 104 MB to 353 MB while its message count and duration stayed flat: a user script was republishing an ever-longer breadcrumb trail, so each message carried more data than the last. Capture was faithful — the topic was the thing growing — but nothing made that visible, and nothing kept it out of the recording.
- **Each cached clip says when and where it was captured.** Rows carried a bare clock reading, so clips from different days looked alike; they now show the date too. Each clip also records a **source label**, shown on its row and saved in the clip's metadata. It fills itself in from the connection when that can be told, and there is a **Source label** box in settings to give it a friendlier name. The label is recorded at the moment of capture, so changing it affects clips taken afterwards and leaves existing ones as they were.
- **Each clip says where its bytes went.** Expanding a cached clip now lists per-topic size next to the message count, largest first, so a topic that is quietly dominating a recording is obvious at a glance.
- **New settings**, under a **Clip cache** node: **Cache limit (MB)** and **Gap trigger (seconds)** (default 10). The number fields report every keystroke, so typing `2048` used to arrive as 2, then 20, then 204 — briefly setting a 2 MB cache limit, which evicted almost everything, or a 2 second lookback, which discarded the buffer. Numbers now only take effect once the field settles. And a settled cache limit lower than what is already cached asks first, in the panel body: "A 512 MB cache limit will drop 3 cached clips (1.4 GB). Apply?" — Cancel puts the old number back.
- **Clip files are named after their clip**, e.g. `diy-dvr-gap-1785781144009.mcap`. **Save all** writes several files in one pass, and the previous `diy-dvr-<now>.mcap` naming would have given them the same name and silently overwritten files. The File System Access permission handshake is unchanged.
- **Storage hardening.** Opening browser storage is now given a deadline, so a host where it hangs no longer leaves the panel waiting forever on "Reading the clip cache…". A clip is given room in the cache *before* it is written rather than after, so a cache at its limit cannot turn into a failed write, and a write that fails halfway no longer leaves an invisible file occupying space. Two panels restarting at the same instant can no longer both claim the same recovery. And a 64-bit number too large for JSON to hold exactly is now recorded exactly rather than silently rounded.
- **Works with or without synchronous file access.** OPFS synchronous access handles are not available in every worker across the web and desktop builds, so the storage wrapper detects support at runtime and implements both the synchronous and asynchronous paths behind one interface. If browser storage cannot be used at all, the panel says so and live capture and saving carry on unaffected.
- **Testable capture core.** The worker's capture logic moved into `captureEngine.ts`, which takes an injected storage backend, clock, and output sink, leaving `mcap.worker.ts` as a thin `postMessage` adapter. This mirrors the existing approach for `settings.ts`. Adds the repo's first test suite — Jest + ts-jest in a Node environment, with 135 unit tests covering the ring buffer, all clip triggers, auto-save rotation durability, session recovery and its resilience to transient storage errors, cache eviction priority (shared by the worker that performs it and the panel that previews it), save-status severity, the save-destination defaults, capture determinism (the same messages always frame to byte-identical output), per-topic byte accounting, topic classification and grouping, backup-heartbeat liveness (including two panels racing to recover the same backup), window ordering under skewed and out-of-order publish times (checked against the MCAP columns that come out), streamed framing (identical output, and never buffering more than a chunk), eviction under a looping source, the hard size ceiling, source-label detection and stamping, and the new settings; CI now runs them.

## 0.2.6

- **MIT licensed.** Replaces the previous proprietary "all rights reserved" LICENSE, so the extension can be distributed through the public [Foxglove extension registry](https://github.com/foxglove/extension-registry). Matches the other Foxglove-published registry entries.
- **Reproducible packaging.** `pnpm run package` now normalizes zip timestamps so a given source tree always produces a byte-identical `.foxe`. The registry pins an exact `sha256sum` per release, and `foxglove-extension package` was stamping the auto-created `dist/` folder entry with the build wall-clock time, so two builds of identical sources hashed differently.
- **CI and release automation.** Pull requests now run lint, typecheck, packaging, the offline MCAP writer check, and a reproducibility check. Tagging `v*` builds the `.foxe`, attaches it to the release, and emits the ready-to-paste `extensions.json` entry for the registry.
- **Housekeeping.** Added `repository` / `bugs` metadata, pinned the package manager, moved pnpm settings out of the `package.json` `pnpm` field (ignored by pnpm >=10) into `pnpm-workspace.yaml` so the `eslint-plugin-import` override applies again, and removed the `pretest` script, which called a `foxglove-extension` subcommand that does not exist.

## 0.2.5

- **Save-handler readability refactor** — the worker `"saved"` callback now delegates to a testable `persistCapture` helper (owns the "try folder → fall back to download" decision, query-only on permission) plus a pure `saveStatusText` mapper, flattening the previously nested async block. No behavior change.
- **Customer-facing docs** — rewrote the README to be concise and user-focused (what it does, features, how to use) instead of implementation internals, since it renders in the app's Extensions view. Replaced the informal package `description` with professional copy.

## 0.2.4

- **Panel-body UI polish** — the save-folder picker now lives solely in the panel Settings "Save destination" select; the in-body "Choose save folder…" button and the Change / Use-browser-download links have been removed (the informational "Save destination" stats row stays). The "Topics, budget, and auto-save are in panel Settings (gear icon)" hint moves to the top of the body, above the button row, so it's the first thing a user sees. Buttons are now square (`borderRadius: 0`) to match Foxglove's UI, and the body reduces to a `Save MCAP` / `Reset buffer` row. No capture, worker, or permission behavior changed.

## 0.2.3

- **Deterministic silent save** — the File System Access write-permission handshake is now only ever *requested* inside a live user gesture (the Save button click, the Auto-save toggle, or the "Save destination" settings action), and the gesture-less worker "saved" callback only ever *queries* the grant. Chromium only grants `requestPermission({mode:"readwrite"})` under transient activation and does not durably keep the grant, so requesting it from the async callback failed silently and fell back to the native Save dialog. Manual **Save** now acquires the grant inside the click and writes silently every time; the permission helper was split into `requestRwPermission` (gesture-only) and `hasRwPermission` (query-only).
- **Honest auto-save** — auto-save rotations write silently while the grant is live; when the grant has lapsed (reload / focus loss / inactivity) they no longer pop a dialog or silently download but show "Auto-save paused — click Save to re-grant folder access". Turning Auto-save on pre-warms the grant inside that toggle gesture and won't enable if permission is denied.
- **Choose-folder is a settings field** — the Saving node's detached "Choose folder…" header action is replaced by a "Save destination" select field (current folder / Choose folder… / Browser download). The in-panel body picker button remains as a reliable gesture path.

## 0.2.2

- **Schema time field matches the data** — synthesized ROS2 schemas now declare the nanoseconds field as `nsec` (e.g. `header.stamp.nsec`), matching Foxglove's decoded message representation and its own `foxglove.*` schemas, instead of the ROS2 IDL name `nanosec`. The panel encodes the decoded object verbatim, so a saved MCAP's schema now agrees with its message data.
- **Silent save no longer prompts** — write permission on the chosen directory is now requested at folder-pick time, inside the user gesture (later saves and auto-save rotations have no gesture, so the request would otherwise fail and fall back to the native Save dialog). A folder is only accepted once readwrite permission is granted.
- **Grouped save-destination settings** — the settings sidebar now has a dedicated "Saving" node holding the Save folder display, the Choose-folder action, and Auto-save, so the picker sits with the controls it relates to rather than at the top of General. Budget mode / Lookback stay in General.
- **Auto-save gated on a save folder** — Auto-save is only shown/enabled once a save folder is set, and the panel never sends `autoSave: true` to the worker without a folder, so a stale persisted flag can't trigger download-dialog rotations.

## 0.2.1

- **Timeline keyed off published time** — the buffered/saved `logTime` now comes from the message's published time (falling back to receive time), so a saved MCAP's timestamps reflect the source clock. The ring buffer is kept sorted by `logTime`, so span reporting and oldest-first eviction stay correct even when a source delivers times out of order (e.g. a looping replay). "Budget used" is floored at zero and can never render negative.
- **Persistent save folder** — the picked directory handle is stored in IndexedDB, so the chosen "Save destination" survives panel remounts and reloads. Permission is re-verified lazily at save time; if it can't be re-granted the save falls back to a browser download but the handle is kept for a later grant.
- **Usable from the panel body** — a "Choose save folder…" button (and Change / Use-browser-download affordances) is surfaced directly in the panel, plus a hint pointing to panel Settings for topics, budget, and auto-save.
- **Native-feeling UI** — the body themes to the app color scheme (light/dark), uses styled buttons and tidy label/value rows, and drops the redundant in-body title.
- **Test server** — `test-server/serve.py` no longer calls `clear_session()` on each loop, so a connected client keeps its channels/topics continuous across the loop boundary instead of dropping them.

## 0.2.0

- **Panel settings editor** — configure the panel from the layout settings sidebar; config is persisted with the layout (`saveState` / `initialState`).
- **Per-topic allowlist** — collapsible Topics node with a toggle per advertised topic (default on); the panel subscribes to only the enabled topics and re-subscribes when the set changes.
- **Lookback budget** — bound the in-memory buffer by max seconds (time mode) or max megabytes (byte mode, measuring the re-encoded JSON payload); the worker evicts the oldest data past the budget.
- **Auto-save on rotation** — when enabled, exceeding the budget snapshots the whole window, clears it synchronously, and frames it to an MCAP instead of dropping data, yielding contiguous rotated files with no gaps.
- **Silent save to a chosen folder** — pick a directory once (File System Access API, Chromium only) and both manual saves and auto-save rotations write `.mcap` files into it silently; falls back to a browser download when unavailable, no folder is chosen, or permission is denied.
- **UI readout** — budget used vs cap, rotation count, capture on/off, topics subscribed, buffered msgs/channels, save destination, and a last-save status line. Save / Reset buttons retained (manual Save is non-destructive).

## 0.1.0

- Initial spin-out from the DIY DVR spike.
- Web Worker capture pipeline: subscribe to live topics, JSON-encode messages (real schemas from the SDK / bundled ROS2 defs, base64 byte arrays), frame to a fully indexed MCAP.
